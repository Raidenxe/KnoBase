## 二、模块一：BM25 混合检索（Hybrid Search）

### 现状
[app/graph/nodes.py](../app/graph/nodes.py#retrieve) 的 `retrieve` 仅走向量检索，之后用 `_lexical_hit` 词法命中率做二次重排加分，并非真正的 BM25 检索路。缺乏"独立关键词召回"能力。

### 设计
引入轻量、离线、可移植的 BM25（Okapi）文本索引，与现有向量检索通过 **RRF（Reciprocal Rank Fusion）** 融合：

1. 新增模块 `app/core/bm25.py`
   - `BM25Corpus`：内存内的 BM25 索引（纯 Python，OKAPI BM25，`b=0.75, k1=1.5`）。
   - 分词：中文按**二元组(bigram)** + 英文数字按词元，复用现有词法归一化风格，不引入 jieba 等重依赖。
   - 构建来源：启动时从 Milvus 全量加载 chunk 文本构建（`build_from_store()`）；入库/删除时增量更新（`upsert_doc_bulk` / `remove_doc`）。
   - 查询：`search(query, top_k)` 返回 `(chunk_id, score)` 候选。
2. 新增 `app/core/retrieval.py` → `HybridRetriever`
   - `retrieve(query_vector, query_text, top_k, bypass)`：并行跑 向量检索 + BM25，做 **RRF 融合** 去重合并。
   - 融合后仍经去重与词法加成精排（保留现有行为），再截断 `retrieval_top_k`。
3. 改造 `retrieve` 节点：调用 `HybridRetriever`，替代原先单一 `store.search`。
4. 配置：新增 `RAG_HYBRID_BM25_K`（BM25 路召回条数，默认 12）、`RAG_RRF_K`（RRF 融合常量，默认 60）。
5. 兼容性：BM25 索引失败/未就绪时自动降级为纯向量检索（与现有哈希降级一致）。

### 涉及文件（新增/修改）
- 新增 `app/core/bm25.py`、`app/core/retrieval.py`
- 修改 `app/graph/nodes.py`（retrieve）、`app/main.py`（启动构建/更新通知）、`app/knowledge/pipeline.py`（入库后刷新 BM25）、`app/core/milvus_store.py`（提供 `all_chunks()` 全量读取）
- 配置 `app/config.py`

## 三、模块二：文档版本管理

### 现状
`ingest_file` 用 `sha1(doc_name::size::mtime)` 生成 doc_id；重新导入同一 doc_id 时**先删后插**（幂等覆盖），无版本历史、无回滚、无"谁在什么时间改过"。

### 设计
新增 SQLite `doc_versions` 库，记录每个文档的每次修订快照；Milvus 只保留"当前激活"版本向量。

1. 新增 `app/services/versions.py` → `DocVersionStore`
   - 表 `doc_versions(doc_id, doc_name, version, fingerprint, chunk_count, source_file, tenant_id, created_by, created_at)`，主键 `(doc_id, version)`。
   - 表 `doc_version_chunks(doc_id, version, chunk_index, section_path, page, text)` 保存每次修订的全文快照（用于回滚/查看历史）。
2. 改造入库：`IngestPipeline.ingest_file` 在入库前读取该 doc 的最近 version + fingerprint；若指纹变化则 `version+1`，写入快照表；Milvus 写入 `chunk_id` 保持格式，但新增 `doc_version` 标量字段。
3. API（挂载到 `/api/v1/documents`）：
   - `GET /{doc_id}/versions`：修订历史列表
   - `GET /{doc_id}/versions/{version}`：指定版本全文
   - `POST /{doc_id}/versions/{version}/rollback`：回滚——用快照恢复该版本为当前激活（重新向量化后覆盖 Milvus，version 再 +1 生成新修订）
4. 兼容性：无 auth 时 `created_by` 为空串；增量跳过逻辑不变（指纹一致的版本不重复生成）。

### 涉及文件
- 新增 `app/services/versions.py`
- 修改 `app/knowledge/pipeline.py`、`app/api/routes/documents.py`、`app/config.py`（`doc_versions_db_path`）
- Milvus schema 增加 `doc_version` 字段（见第六节 Schema 变更）

## 四、模块三：多租户与权限控制 RBAC

### 现状
完全无认证/用户/租户/权限。所有接口裸奔（`/chat`、`/documents`、`/conversations`）。

### 设计
采用「可选开启 + 默认关闭」策略，保证演示与既有测试零改动即可运行：

1. 新增认证库 `app/services/auth_store.py`（SQLite `auth.db`）
   - `users(id, username, password_hash, display_name, tenant_id, role, is_active, created_at)`
   - `tenants(id, name, created_at)`
   - `user_roles`：`admin`(跨租户/系统管理) | `owner`(租户内全权) | `member`(租户内读写) | `viewer`(租户内只读)
   - 密码存 `bcrypt`/`pbkdf2` 哈希；依赖 `passlib[bcrypt]`。
2. 认证方式：JWT Bearer Token（`PyJWT`）。签发 `POST /api/v1/auth/login`，刷新、登出（黑名单可选）。
3. 租户隔离：Milvus chunk、conversation、doc 均增加 `tenant_id` 标量字段；所有文档/会话读写按当前用户 tenant 过滤（Milvus filter 表达式 + SQL where）。
4. RBAC 依赖/中间件 `app/core/security.py`：
   - `get_current_user` 依赖解析 Bearer Token → user 对象
   - `require_role(*roles)`、`require_tenant_scope` 装饰器式守卫挂在各路由。
   - 演示模式（`RAG_AUTH_MODE=off`，默认）时依赖自动放行，行为与现在完全一致。
5. 路由挂载：`/chat`、`/documents`、`/conversations`、`/tasks` 按最小权限收口。
6. Milvus schema 增加 `tenant_id` 字段；既有库需重建集合（见第六节）。

### 涉及文件
- 新增 `app/services/auth_store.py`、`app/core/security.py`、`app/api/routes/auth.py`
- 修改 `app/config.py`、`app/main.py`（挂 auth 路由与中间件）、`app/api/routes/*`（接入守卫+租户过滤）、`app/core/milvus_store.py`、`app/services/history.py`
- requirements 增加 `PyJWT`、`passlib[bcrypt]`

## 五、模块四：WebSocket + 全链路追踪 / 评估

### WebSocket 实时问答
- 新增 `app/api/routes/ws.py`：`WS /api/v1/ws/chat`
  - 客户端发送 `{question, conversation_id, token?}` → 复用 `chat_service.chat_stream`，把每个 SSE 事件包装为 JSON 帧推送；`done`/`error` 语义对齐现有 SSE 协议。
  - 复用同一认证依赖（auth 开启时校验 token）。

### 全链路追踪与监控
1. 请求链路 ID：全局中间件 `app/core/tracing.py`
   - 每位请求生成 `trace_id`（可传 `X-Request-Id`），写入 `X-Request-Id` 响应头；结构化日志（`trace_id`）贯穿各节点。
2. Span 记录：在 `analyze / retrieve / grade / generate / verify` 各节点开始与结束时打点（开始已有 `*_ms` 指标，补上 trace_id 与上下文）。
3. 新增 `TraceStore`（内存环形缓冲 + 可选落库 `trace.db`）：存 `trace_id → [stages]`，供
   - `GET /api/v1/traces/{trace_id}` 查看一次请求全流程阶段耗时
   - `GET /api/v1/metrics/basic` 汇总（分阶段 P50/P95/峰值、检索召回条数、答案失败/拒答率）
4. 在 SSE/WS 的 `status` 事件与 `done.metrics` 中附 `trace_id`，便于前端与运维对账。

### 评估体系 Evaluation
1. 新增 `app/eval/registry.py` 与 `scripts/eval.py`
   - 定义小规模评估集（`(question, gold_doc_ids / gold_chunks)`），放置于 `eval/dataset.jsonl` 起步约 10–20 条示例。
   - 计算指标：命中 `Hits@k`、`Precision@k`、`Recall@k`、`MRR@k`（针对检索），以及端到端答案的"引用命中 gold 的比例、拒答/幻觉率"。
   - 输出 `eval/report_<ts>.json` + 控制台表格。
2. 提供 `GET /api/v1/eval/summary`（仅 admin，返回最近一次评估摘要；不占运行时开销）。
3. 配套 pytest：对 BM25、RRF 融合、检索指标函数、trace store、版本管理、RBAC、WS 的**关键路径**补单测，新增 `tests/test_hybrid.py / test_versions.py / test_auth_rbac.py / test_ws_trace.py / test_eval_metrics.py`。

### 涉及文件
- 新增 `app/api/routes/ws.py`、`app/core/tracing.py`、`app/services/trace_store.py`、`app/api/routes/observability.py`、`app/eval/`、`scripts/eval.py`、`eval/dataset.jsonl`
- 修改 `app/main.py`、`app/graph/nodes.py`（打点）、`app/services/chat_service.py`（WS 复用 + trace 透传）、`app/config.py`
