# 运维四件套 · 开发计划

> 状态：✅ 已实施 · 范围：**资源水位监控 / 模型切换 / 检索参数调整 / 慢请求明细拆分**（后端 + 前端 + 文档已交付）
> 前置结论：核心配置当前为**启动时静态加载**（`get_settings()` 走 `@lru_cache`，LLM/Embedding 均为进程级单例）。
> 本计划引入**运行时动态配置层**，使模型切换与检索参数调整**无需重启即可生效**。
> 遗留项（本轮不做）：自助注册、知识库分类/权限/批量增删改、插件式文档 Web 浏览。

## 一、通用基础：运行时动态配置层

**新增 `app/core/runtime_config.py`**（内存单例，线程安全）

- 保存一组可覆盖字段，初始值 = `.env` 静态值；`get(field, default)` 优先返回动态覆盖值。
- 覆盖字段（与原 config 字段同名）：
  - **LLM**：`llm_provider / llm_base_url / llm_api_key / llm_model / llm_temperature`
  - **Embedding**：`embedding_provider / fastembed_model / embedding_api_base / embedding_api_key / embedding_model`
  - **检索**：`retrieval_top_k / retrieval_score_threshold / keyword_overlap_min / max_context_chunks / hybrid_bm25_k / rrf_k / rerank_enabled / rerank_top_k / rerank_keep`
- 提供：
  - `get(field, default=None)` / `set(field, value)` / `reset(field)` / `snapshot()`
  - `get_settings()` 的替代入口：新增 `app/core/settings_rt.py#effective_settings()`（返回一个可覆盖的 Settings 视图），供 nodes/retrieval/rerank 读取，避免逐一改写 `settings.xxx`。

**读写接入（最小侵入）**

- `nodes.py` `retrieve`：`settings.retrieval_top_k / retrieval_score_threshold` → `effective_settings()`（RRF/rerank 交由 retrieval/rerank 内部读取，此处只传 top_k 与阈值）。
- `retrieval.py`：`hybrid_bm25_k / rrf_k / rrf_vector_weight / rrf_bm25_weight` → 动态。
- `rerank.py`：`rerank_enabled / rerank_top_k / rerank_keep` → 动态；`get_reranker()` 的懒加载开关改为每次按 `rerank_enabled` 判定（否则切换开关无效）。
- `llm.py`：`is_mock`、`_acomplete`、`astream_answer` 的 `model/temperature` 改读动态值；暴露 `llm_service.reload()` 用当前动态 LLM 配置重建 `AsyncOpenAI` client（mock↔openai 互相切换）。
- `embeddings.py`：暴露 `rebuild_embedder()`，按当前动态字段重建并替换进程单例；**维度变化时返回 `dimension_changed` 标记**，前端提示"需重建 Milvus 集合"。

> 兼容性：动态层默认值恒等于静态配置，全功能局外（auth off/demo）行为零变化；不写进 `get_settings()` 底层，不动其他读取点。

## 二、模块 1：资源水位监控（CPU / 内存 24h 曲线）

**后端**
- 新增 `app/services/resource_monitor.py`
  - 后台守护线程每 10s 用 `psutil` 采集：CPU 使用率、内存（used/total）、磁盘占用、进程 RSS。
  - 落地 SQLite `data/resource.db`（表 `samples(time_bucket, cpu, mem_used, mem_total, disk_used, disk_total, rss)`），每 60s 聚合为一条；同时保留内存环形缓冲（最近 24h）。
  - 启动时随 lifespan 拉起；退出自动停止。
- 新增接口（挂 `observability.py`，均 `admin_required`）：
  - `GET /api/v1/admin/resource/current` → 当前即时读数。
  - `GET /api/v1/admin/resource/series?hours=24&step=60` → 聚合曲线数据点 `[{ts, cpu, mem_used, mem_total}]`。
- `requirements.txt` 追加 `psutil`。

**前端 `admin.html`**
- 新增 Tab「资源水位」(data-tab=`sys`)，面板含：即时卡片（CPU/内存/磁盘/进程RSS）+ 24h 曲线（CPU%、内存占比双轴）。
- 引入 **Chart.js**（CDN，`window.Chart` 缺失时降级为纯 canvas 折线手绘），与 browser.html 的 CDN+fallback 风格一致。
- `setInterval` 每 15s 刷新即时读数，曲线每 60s 拉一次全量系列。

## 三、模块 2：模型切换（运行时切换 LLM / Embedding）

**后端**
- 新增 CRUD-风格管理路由（挂 `observability.py`，`admin_required`）：
  - `GET /api/v1/admin/models` → 当前 LLM / Embedding 动态配置、`is_mock`、dimension、可用预设。
  - `PUT /api/v1/admin/models/llm` → body `{provider, base_url, api_key, model, temperature}`；写动态层后调用 `llm_service.reload()` 立即生效。
  - `PUT /api/v1/admin/models/embedding` → body `{provider, model, api_base, api_key}`；调 `rebuild_embedder()`；返回 `dimension_changed`。
- `core/llm.py`：`reload()` 用当前动态值重建 client，刷新 `provider/is_mock`；校验 openai 缺 key 时回退 mock。
- `core/embeddings.py`：`rebuild_embedder()` 替换进程单例；维度与当前 Milvus 维度不一致 → 返回警告；query/documents 用新单例。
- Embedding 维度变化的重建机制沿用 `scripts/migrate_schema.py`（本次提供接口提示，不自动重建，避免误伤）。

**前端 `admin.html`**
- 新增 Tab「模型切换」(data-tab=`model`)：LLM 区块（provider 下拉、base_url、api_key、model、temperature + 保存即生效）、Embedding 区块（provider、model、api_base、api_key + 保存）。
- 保存前基础校验；响应含 `dimension_changed` 时弹确认提示。

## 四、模块 3：检索参数可视化调整（Top-K / 阈值 / Rerank）

**后端**
- 新增（挂 `observability.py`，`admin_required`）：
  - `GET /api/v1/admin/retrieval` → 当前 `retrieval_top_k / retrieval_score_threshold / keyword_overlap_min / max_context_chunks / hybrid_bm25_k / rrf_k / rerank_enabled / rerank_top_k / rerank_keep`（含动态覆盖标记）。
  - `PUT /api/v1/admin/retrieval` → 部分更新上述字段到动态层，即时生效；支持 `{field: null}` 逐项重置回默认。
- 检索链路已接入 `effective_settings()`，故保存后下一请求即用新参数（无需重启）。
- rerank 开关切换即时生效（依赖 `rerank.py` 的懒加载判定改动）。

**前端 `admin.html`**
- 新增 Tab「检索参数」(data-tab=`param`)：数值/开关表单，含重置单字段按钮；保存调 `PUT` 并刷新当前值显示。
- 展示当前生效值与默认值的差异标记。

## 五、模块 4：接口慢请求明细拆分（单请求耗时分解面板）

**后端**
- `services/trace_store.py`：`add_span` 支持 `detail` 字段（可选 dict）；`recent()` / `get()` 返回 detail。
- `nodes.py` `retrieve` / `generate` 补充子段：
  - `retrieve` span 附加 `{hits, vec_ms, bm25_ms, rerank_ms, threshold}`（由 retrieval.py/hybrid_retrieve 返回各段计时）。
  - `generate` span 附加 `{llm_ms, tokens_estimate}`（LLM 服务统计生成耗时）。
- 新增 `GET /api/v1/traces/{trace_id}/detail` → 返回单次请求的阶段拆分（analyze/retrieve[含子段]/grade/generate/verify + 总耗时 + 状态），供"分解面板"。
- 现有 `GET /api/v1/traces`（列表）与 `/metrics/basic`（聚合）保持不变。
- `tracing.py` 中间件：对全程 > 阈值（可配，默认 500ms）的请求，额外把 trace_id 与全程耗时并写入一个"慢请求"轻量表/内存队列，供「慢请求明细」Tab 直接取用。

**前端 `admin.html`**
- 增强现有「链路耗时」Tab（data-tab=`trace`）：除现有表格外新增"慢请求明细"子区，列出近 N 条慢请求。
- 点击某条 → 展开**单请求拆分解板**：可视化阶段横条（analyze → retrieve[vec|bm25|rerank] → grade → generate[llm] → verify），每条显示耗时、命中条数、阈值；高低耗时着色。
- 复用现有 `trace`/`metrics/basic` 数据 + 新增 `/detail`。
